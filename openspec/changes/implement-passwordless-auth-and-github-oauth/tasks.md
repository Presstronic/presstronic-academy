## 8. Security Mitigations (In-Scope Risks from proposal.md)

- [ ] 8.1 Implement two-step magic-link consume: `GET /auth/link?tid=…` returns an HTML landing page with a `Sign in` button that `POST`s the token to `/auth/magic-link/consume`; the landing response sets `Referrer-Policy: no-referrer` and includes a `<meta name="referrer" content="no-referrer">`; requests whose `User-Agent` matches a known email-scanner heuristic (Microsoft Defender, Barracuda, Mimecast, Proofpoint) render the page without pre-consuming. Verify integration tests cover: normal browser renders + consumes on POST, scanner UA renders but does not consume, response headers include the referrer policy.
- [ ] 8.2 Implement JWT signing with `kid` header + JWKS: `AccessTokenService` reads a keyset (active + retired) from configuration and signs with the active `kid`; the verifier accepts any `kid` in the keyset; expose `GET /.well-known/jwks.json` for verifier-side rotation. Verify a unit test covers mint-with-active-kid, verify-with-retired-kid, reject-unknown-kid; and an integration test hits the JWKS endpoint and validates its shape.
- [ ] 8.3 Implement same-origin startup assertion: on `ApplicationReadyEvent`, compare configured `academy.web.origin` and `academy.api.origin` registrable domains (via `com.google.guava:guava` `InternetDomainName` or equivalent) and throw a startup failure if they differ. Verify an integration test asserts a mismatched configuration fails to start and a matched configuration starts cleanly.
- [ ] 8.4 Implement dev-endpoint profile guard: on `ApplicationReadyEvent`, if the application context contains a `DevMagicLinkController` bean AND `spring.profiles.active` contains `prod` or `staging`, throw a startup failure. Verify integration tests cover: `local` profile starts with the controller, `prod` profile starts without the controller (bean absent), a misconfigured `prod,dev` combo fails to start.
- [ ] 8.5 Add a CI guard script (`scripts/ci/check-deploy-profiles.sh` or equivalent) that greps deployment configs (`apps/api/src/main/resources/application-*.yml`, any `k8s/` or `deploy/` config we own) for the forbidden `prod` or `staging` + `dev` or `local` profile combination and exits non-zero on a match; wire it into the root `package.json` scripts. Verify the script fails when handed a fixture with the forbidden combo and passes on the current tree.
- [ ] 8.6 Implement strict `returnTo` allowlist on `GET /oauth/github/authorize`: accept only same-origin absolute URLs whose path starts with a configured allowlist prefix (`/`, `/dashboard`, `/lesson`, `/story`, `/log`, `/progression`, `/profile`, `/catalog`, `/certificate`). Values outside the allowlist are silently coerced to `/`. Verify unit tests cover each allowlisted prefix, an off-origin URL, a scheme-mismatch URL, and a path-traversal attempt.
- [ ] 8.7 Emit a structured `identity_linked` audit event whenever GitHub OAuth callback links a new identity to an existing account: include `account_id`, `identity_kind`, `external_id`, `linked_at`, `source_ip`, `user_agent`. Persist to a new `identity_events` table (add to `V1__auth_baseline.sql` or `V2__identity_events.sql`). Verify an integration test asserts the row is written on auto-link and not written on same-identity re-sign-in.
- [ ] 8.8 Add a global request-floor bucket per public auth endpoint (independent of email/IP keys): `mlreq:global` (e.g. 1000/min), `mlcon:global` (e.g. 2000/min), `oauth:global` (e.g. 1000/min). Bucket keys and limits live in `AcademyAuthProperties`. Verify integration tests assert the global bucket kicks in even when per-key buckets have headroom.
- [ ] 8.9 Log every refresh-token grace-window hit as a `refresh_grace_hit` security event with `session_id`, `family_id`, `previous_token_id`, `presenting_ip`, `presenting_user_agent`, and `age_ms_since_used_at`. Structured log field prefix `security.event`. Verify an integration test drives the grace-window race and asserts exactly one event is emitted.
- [ ] 8.10 Rework magic-link enumeration protection: route registered and unregistered branches through the same `MagicLinkService.request` code path with a shared constant-time hashed-token insert (real row for registered, discard-sink row for unregistered); replace the 0–50ms random jitter with a fixed-latency floor (e.g. 200ms) applied in the controller after the service completes. - [ ] 8.11 Record `user_agent` and coarse `network_fingerprint` (e.g. `/24` for IPv4, `/64` for IPv6) on the `sessions` row at creation.
